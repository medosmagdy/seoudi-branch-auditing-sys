# Maintenance section

The new /maintenance section has three tabs: indicators, branch cards and the master observations log. It follows the current application theme and existing section visibility administration. Administrators have access by default; another active account needs an explicit maintenance grant. This grant permits reading/creating/editing/duplicating/deleting maintenance reports, editing findings and exporting. It does not change audit access or branch scopes.

## Authoritative snapshot
The index RPC selects exactly one **submitted** report per branch, ordered by inspection date descending, creation timestamp descending, then UUID descending. This happens BEFORE branch/severity/status/search filtering. Draft copies and historical reports never contribute to the log or indicators. A more recently entered report with an older inspection date cannot replace a newer inspection. Same-date revisions use creation order. Deleting the current report exposes the previous submitted report and the confirmation explicitly explains that behavior. Branch cards show the last submitted inspection and current unresolved/high-risk counts.

The new-report and duplicate actions create drafts. Duplicate copies all findings, including resolved statuses, initial history, corrective actions, evidence, comments, assigned person, target dates and photos, with independent finding IDs. Saving/submitting is atomic. Submitting a report with no observations requires an explicit UI confirmation and represents a clean latest snapshot, so older findings cannot reappear merely because the latest report has no findings. A report version guards against overwriting another user's changes. Report branch cannot change after creation. Submitted reports remain editable as requested. Removal changes only that report; no historical records are automatically edited.

Closure = resolved / all current findings after filters; empty results show a dash rather than a fabricated percentage. Unresolved includes new/open/in-progress; high-risk KPI counts unresolved high findings. Overdue means unresolved with a target date before today in Africa/Cairo; no deadline is inferred from the original fault history. Statuses retain the reference workbook's تم / لم يتم / جديد with an additional قيد التنفيذ.

## Reference and exports
The supplied Sheraton workbook was reviewed read-only. Its 69 findings (36 resolved, 33 unresolved) were used to identify the form/export fields: section, maintenance point, original fault history, severity, corrective action, objective evidence, status, comments and photos. No supplied business observations or images are committed or seeded. The supplied workbook was not modified or automatically imported.

Every report can export saved content to PDF and Excel, including pictures. PDFs render bounded groups of three findings instead of one excessively tall canvas. Export controls are omitted. Excel includes all fields plus branch/inspection, assigned person, target date and numbered embedded images on a related-pictures sheet. The exported log respects all active filters. Excel image export is capped at 300 images per operation with an explicit instruction to filter/export batches; it never silently omits images. Formats use the inspection quarter/year in filenames. Missing/failed image retrieval blocks incomplete exports. Outlook/maintenance email composition remains deferred.

## Photos
Photos use the existing Cloudflare R2 server credentials; no client secrets or new environment values. Server handlers verify the actual Supabase session and active-account section access before issuing upload/read URLs. A server-only photo directory records generated keys. Registration checks the stored JPEG MIME type and 8MB maximum before allowing report references. Read operations sign only registered directory keys, with bounded concurrency and one-hour expiry. User files accept JPEG/PNG/WebP and are compressed to JPEG before uploading.

Removing photos detaches references; physical R2 objects and directory entries are retained so quarterly copies/history are not broken. Cancelling an upload/editor may leave an unreferenced object. Garbage collection is deliberately outside this change. No existing audit/expiry photo functions or deletion behavior are modified.
