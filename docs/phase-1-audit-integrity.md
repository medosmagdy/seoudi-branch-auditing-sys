# SQOP — الدفعة الأولى: سلامة اعتماد الفحوصات

## نطاق التغيير

مبنية على commit `f4464efd1e9bd61c6c2a4b0ab6bdbfb9a93a31b2`، وهو مطابق للنسخة المرفوعة وقت المراجعة.

- الاعتماد يستخدم أسئلة التقرير الحالي فقط؛ تحميل التقرير يحدد البرنامج باستخدام `audit_type_id` ويحدد الأسئلة والأقسام النشطة.
- البنود غير المسجلة تحصل على `max_score` كما كان مقصودًا. `ignoreDuplicates` يحافظ على الإجابات المحفوظة، ومنها الخصومات وN/A، حتى لو أُضيفت إجابة أثناء الاعتماد.
- يتم التحقق من أخطاء القراءة والحفظ وعدم الاعتماد عند فشلها، مع إعادة حساب النتيجة من البيانات المحفوظة قبل تحديث حالة الفحص.
- فتح الفحص والتقرير يطلب إجابات البرنامج نفسه فقط، على صفحات مرتبة، لتجنب تنزيل الإجابات الدخيلة وتجنب حد الصفوف الصامت.
- إعادة القراءة أثناء الاعتماد لا تحمل الصور. تحميل التقرير العادي يظل يعرض الصور.
- لا تعديل لمحرك `computeAudit` أو معادلاته أو قواعد التوصيل أو الدرجات الافتراضية أو تصميم الفحص.
- لا حذف بيانات أو تعديل Supabase أو RLS أو نشر للموقع ضمن هذه الدفعة.

## النتائج المؤكدة من الملفات

البيانات المرسلة تحتوي 82 فحصًا و57,580 إجابة و1,004 أسئلة. الاستعلام أحصى 44,793 إجابة يختلف برنامج سؤالها عن برنامج الفحص؛ لم يفحص قيمها الفردية، وبالتالي لا يثبت أن جميعها آمنة للحذف.

المعرف `audit_type_id` يربط الفحص بالبرنامج. تصنيف العرض في `dashboard/metrics.ts` يستخدم كذلك أكواد/أسماء البرامج ومعرفات ثابتة، ويرجع FS عند عدم التعرف على البرنامج. الفروع والمخازن تُفصل بأسماء المكان/البرنامج. لا يوجد حقل cadence ولا منطق جدولة شهرية/ربع سنوية في المسارات المراجعة. لا يجوز استنتاج البرنامج ربع السنوي من اسمه وحده.

درجة `audits.score` و`overall_score` كانت تُكتب عند الاعتماد فقط. مسارات تعديل الإجابات وحالة القسم والخصومات لا تعيد كتابتها. التقرير يحسب النتيجة مباشرة، بينما قوائم/تاريخ تقارير ومؤشرات أخرى قد تستخدم القيم المحفوظة. هذه الدفعة تضمن تحديثها عند إعادة الاعتماد، **ولا تصلح بعد المزامنة التلقائية لكل تعديل على فحص معتمد**. يلزم إصلاح مستقل بعد حصر جميع مسارات التعديل، مع الحفاظ على معادلة الحساب الحالية.

ميزة RLS معطلة على عدة جداول أساسية بحسب البيانات المرسلة. لم تُفعّل هنا. وظائف تغيير الرتب والحذف ذات `SECURITY DEFINER` تحتاج مراجعة منح EXECUTE والتحقق الداخلي من Admin قبل أي نشر لإصلاح الصلاحيات.

كود رفع الصور الحالي يتضمن بيانات اعتماد R2 في كود يصل للمتصفح، بما فيها fallback مكتوب في المصدر. ينبغي تدوير بيانات الاعتماد ونقل عمليات التخزين ذات الصلاحية إلى السيرفر؛ مجرد إزالة النص أو استخدام متغير يبدأ بـVITE_ لا يحمي السر. لم يتم استعمال بيانات الاعتماد أو نسخ قيمها إلى هذا التقرير.

## التحقق قبل الدمج

1. في بيئة اختبار منفصلة، افتح فحصًا لكل برنامج وقارن النتيجة والصور والتقرير قبل وبعد التعديل، بدون تغيير الإجابات.
2. سجل خصمًا وN/A، واعتمد الفحص؛ يجب بقاء القيم وعدم استبدالها بالدرجة الكاملة.
3. قارن عدد إجابات الفحص قبل وبعد الاعتماد: الإضافات يجب أن تخص برنامجه فقط، وعدم تكرار الصفوف عند إعادة الاعتماد.
4. اختبر فشل قراءة وحفظ؛ لا يجب أن يظهر نجاح اعتماد لعملية فاشلة.
5. لا تعتمد Preview متصلًا بقاعدة الإنتاج كبيئة اختبار معزولة.

يوجد ملف SQL قراءة فقط في `supabase/diagnostics/audit-programs.sql` لمعرفة هويات البرامج، ونشاطها الشهري، وطبيعة الإجابات المتأثرة، ومنح الوصول الفعلية. ليس migration ولا يُنفذ تلقائيًا.

## حدود هذه الدفعة

الاعتماد ما زال عدة طلبات، وليس transaction واحدة في قاعدة البيانات. فشل خطوة حفظ النتيجة بعد إضافة الافتراضيات يترك الفحص بحالته السابقة ويمكن إعادة المحاولة؛ لا يدعي هذا التغيير حماية كاملة من تعديل متزامن في جهاز آخر.

الـDashboard نفسه ما زال يستخدم التحميل الكامل القديم. فصل المؤشرات وتجميعها في قاعدة البيانات، ومعالجة 100% عند غياب البيانات وطريقة دمج البرامج، إصلاحات لاحقة تحتاج تثبيت تعريف الحساب مع صاحب المشروع.

ملف package-lock الحالي لا يطابق package.json، وبالتالي فشل npm ci في النسخة الأصلية. استُخدم npm install --package-lock=false --ignore-scripts للتحقق المحلي دون تغيير ملفات الإصدارات. يلزم توحيد مدير الحزم وملف القفل في دفعة مستقلة.

## نتائج التحقق المحلي

- نجح 9 اختبارات في 3 ملفات، تشمل فشل الحفظ/القراءة، احترام برنامج الفحص، وعدم استبدال الإجابات المحفوظة بالافتراضيات.
- نجح ESLint للملفات الجديدة وإعداد الاختبارات.
- نجح npm run build لإنتاج نسخة النشر، مع تحذيرات البناء الموجودة بالمشروع.
- مقارنة TypeScript مع commit الأصلي باستخدام نفس الاعتماديات: 65 تشخيصًا قبل التعديل و60 بعده، دون رسائل أخطاء جديدة بعد تجاهل تغير أرقام الأسطر. لم ينجح فحص TypeScript العام بسبب أخطاء سابقة في المشروع، منها عدم تطابق تعريفات قاعدة البيانات.
- لم تُجر اختبارات متصلة بقاعدة الإنتاج، ولم يُنفذ ملف التشخيص SQL.

## التطبيق محليًا

ملف ZIP الخاص بهذه الدفعة يحتوي الملفات المضافة والمعدلة فقط، بمساراتها داخل المشروع؛ يُفك داخل مجلد المشروع الحالي مع استبدال الملفات المناظرة. لا يحتوي مفاتيح بيئة ولا نسخة من البيانات ولا يتطلب تشغيل SQL. احفظ تغييراتك المحلية أولًا، واستخدم فرعًا منفصلًا، ثم جرّب واعمل PR قبل الدمج.

الرجوع يتم باسترجاع commit هذه الدفعة فقط. لا يوجد تغيير لقاعدة البيانات يحتاج rollback.
