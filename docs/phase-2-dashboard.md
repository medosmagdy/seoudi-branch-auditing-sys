# SQOP — الدفعة الثانية: ملخص سريع للـDashboard

## ما يتغير

هذه الدفعة تخص لوحة التحكم وتجميعاتها فقط. لا تعدل `scoring.ts` ولا صفحات الفحص أو الاعتماد أو التقارير. تستخدم محرك الفحص الحالي نفسه لتحويل مجاميع النقاط إلى نسب، ولا تحدث حقول درجات الفحص في قاعدة البيانات.

الأرقام الرئيسية تطلب snapshot واحدًا مستقلًا. PostgreSQL يجمع النقاط والأسئلة الافتراضية وN/A وخصومات الأقسام والخصم العام للفترة والموقع المطلوبين، ويرجع بيانات مضغوطة لكل فحص/قسم. لا ينقل الإجابات الفردية أو التعليقات أو الصور. الدرجات المحفوظة القديمة في audits ليست مصدر هذا الملخص.

بعد ظهور المؤشرات، تبدأ تفاصيل الفترة المختارة في الخلفية. استعلامات التفاصيل تفلتر التاريخ والموقع والبرنامج قبل تنزيل الإجابات، وتستبعد إجابات البرامج الأخرى والأقسام المستثناة والأسئلة غير النشطة. تبويب المتابعة لا يطلب الإجابات. الكاش منفصل حسب الحساب والنطاق والفلاتر، ولا يعيد تحميل التفاصيل عند التركيز على النافذة. الرجوع للصفحة يعيد قراءة الملخص، ويوجد زر تحديث.

## الحساب المتفق عليه

- الشهور 1، 2، 4، 5، 7، 8، 10، 11: FS بوزن 50% وGHP بوزن 50%.
- الشهور 3، 6، 9، 12: FS بوزن 50% وGHP بوزن 40% وFSMS بوزن 10%.
- الزيارات المعتمدة فقط تدخل النسبة؛ المسودات تُعد منفصلة.
- عند تكرار البرنامج لنفس الفرع والشهر يُحسب متوسط نتائجه أولًا.
- بعد أوزان الشهر، تتساوى الشهور داخل الفرع ثم تتساوى الفروع، بدون إعطاء وزن أكبر لفرع عنده زيارات أو أسئلة أكثر.
- نقص برنامج مطلوب أو عدم وجود درجات قابلة للحساب يعطي «غير مكتمل»، وليس صفرًا أو 100% أو إعادة توزيع الأوزان.
- إذا كان بعض الفروع/الشهور غير مكتمل، لا تُعرض نسبة مكتملة للمجموعة كلها. التفاصيل تعرض البرامج المتاحة ومتوسط التقييمات المكتملة بعنوان صريح منفصل.
- قبل الخصومات يعني قبل خصومات الأقسام والخصم العام. بعد الخصومات يعني بعدهما. قواعد استثناء الأقسام والتوصيل مطابقة لمحرك الفحص الحالي.
- أي برنامج غير معروف يُعرض كتحذير، ولا يصنف FS تلقائيًا.
- كارت الامتثال وتفاصيله والملخص التنفيذي في تصدير Dashboard يستخدمون النتيجة المجمعة الجديدة. مؤشرات الأقسام التفصيلية تبقى مؤشرات نقاط الأقسام، وليست أوزان البرامج في الكارت الرئيسي.

مثال شهر عادي: FS=90 وGHP=80 تعطي 85%. مثال شهر سبتمبر: FS=90 وGHP=80 وFSMS=70 تعطي 84%. غياب FSMS في سبتمبر يعطي «غير مكتمل».

## التطبيق بالترتيب

1. احفظ نسخة من مشروعك الحالي، واستخدم فرعًا ورابط Preview للتجربة. لا تعتبر Preview مع نفس قاعدة الإنتاج بيئة بيانات منفصلة.
2. في Supabase SQL Editor شغّل كامل الملف `supabase/migrations/20261023190000_dashboard_snapshot.sql` أولًا. ينشئ وظيفة قراءة واحدة ويمنحها للمستخدمين المسجلين مع تحقق داخلي من Admin/Manager نشط. لا يشغّل UPDATE/DELETE على البيانات، ولا يفعّل RLS، ولا يغير سياسات الجداول أو وظائف الحساب الحالية. يمكن إعادة تشغيله.
3. فك ZIP الدفعة داخل جذر المشروع مع الحفاظ على المسارات واستبدال الملفات المناظرة، ثم اختبر البناء والـPreview قبل الدمج.
4. افتح Dashboard بحساب Admin ثم Manager. تحقق من الشهر الحالي والفروع والمخازن، وافتح الامتثال لترى قبل/بعد ونقص البرامج. تحقق أن الحساب Auditor لا يفتح Dashboard.
5. من Network، تأكد من ظهور طلب `sqop_dashboard_snapshot` مستقل قبل طلبات تفاصيل الإجابات، وأن التفاصيل تقتصر على الفحوصات المختارة. قارن أوقات الطلبات على قاعدة الإنتاج؛ لم يُجر قياس إنتاجي من بيئة التطوير.

التغييرات الإضافية في SQL لا تعطل الواجهة القديمة. عند الرجوع، ارجع ملفات هذه الدفعة أولًا؛ يمكن ترك وظيفة القراءة غير المستخدمة، أو حذفها لاحقًا:

```sql
DROP FUNCTION IF EXISTS public.sqop_dashboard_snapshot(text, date, date, uuid);
```

لا تحذف الوظيفة بينما الواجهة الجديدة منشورة. لا تتطلب هذه الدفعة تشغيل ملفات migrations القديمة أو تشخيص/تنظيف الإجابات. ZIP الدفعة الثانية يقتصر على ملفات Dashboard واختباراته ووظيفة القراءة وتعليماته؛ ليس مطلوبًا إعادة تطبيق ملفات الفحص من الدفعة الأولى.

## الاختبارات والقيود

اختبارات الوحدة تغطي الأوزان، قبل/بعد، التكرار، غياب البرامج، عدم إعادة توزيع الأوزان، مساواة الفروع والشهور، وعينات مقارنة مع محرك الفحص الأصلي. اختبارات محمل التفاصيل تتحقق من فلاتر السيرفر واستبعاد البرامج الأخرى وN/A وعدم طلب الإجابات للمتابعة.

يوجد اختبار تكامل على PostgreSQL/WASM معزول (PGlite) ينفذ ملف SQL الفعلي ويفحص الافتراضيات وN/A والخصومات، وتحديث الملخص بعد تعديل الإجابة دون كتابة الدرجة المحفوظة، وصلاحيات الأدوار والنطاقات، وعدم تغير البيانات المنقولة عند إضافة 1000 إجابة من برنامج آخر. لا يتصل بقاعدة الإنتاج. لتشغيله، ثبت `@electric-sql/pglite` في مجلد منفصل، واضبط SQOP_PGLITE_MODULE لمسار dist/index.js ثم شغّل npm test. من دون المتغير تُتخطى اختبارات SQL فقط.

الـDashboard يقرأ تعريف الأسئلة والأقسام النشطة الحالي، مثل تقرير الفحص الحالي. تجميد نسخ قوائم الفحص التاريخية ليس ضمن هذه الدفعة. كما أن إصلاح RLS العام ووظائف الإدارة وبيانات اعتماد الصور يحتاج دفعة منفصلة؛ حماية وظيفة الملخص الجديدة لا تصلح صلاحيات endpoints القديمة تلقائيًا.

عند مسح التاريخ، تؤخذ الأشهر بين أقدم وآخر فحص في الاختيار، أو الشهر المحدد بالطرف المتاح إذا لا توجد فحوصات، أو الشهر الحالي عند غياب الطرفين والبيانات. قد يزيد حجم الملخص عند اختيار تاريخ طويل، لكنه لا ينقل الإجابات الفردية.

## نتيجة التحقق لهذه النسخة

نجح 40 اختبارًا في 6 ملفات، بما فيها تنفيذ SQL على PostgreSQL معزول. نجح بناء نسخة النشر وESLint للملفات الجديدة ومحمل التفاصيل. فحص TypeScript العام ما زال يعرض 60 تشخيصًا سابقًا كما في نهاية الدفعة الأولى، دون رسائل جديدة بعد تجاهل تغير أرقام الأسطر. لم تُغير ملفات قفل الحزم القديمة غير المتطابقة مع package.json.

تم التحقق من أن ملفات محرك الفحص وصفحات الفحص والتقرير والاعتماد لم تتغير مقارنة بنهاية الدفعة الأولى. لا توجد نتيجة زمن استجابة مقاسة على قاعدة الإنتاج، ولا يتضمن نجاح اختبارات PostgreSQL المحلي ضمانًا لأداء الشبكة أو خطة التنفيذ في الإنتاج.
