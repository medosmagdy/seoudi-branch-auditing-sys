# SQOP — Phase 3: متوسط المتاح، الفلاتر وترتيب الفروع

## نطاق الدفعة

تخص Dashboard فقط، فوق نهاية الدفعة الثانية وإصلاح استدعاء RPC (`f228be5`). لا تغير محرك الفحص ولا صفحاته أو تقاريره، ولا تحتاج SQL جديدًا أو تعديل RLS. تستمر باستخدام وظيفة القراءة `sqop_dashboard_snapshot` المطبقة في الدفعة الثانية. تقرير المفتش داخل الإدارة مؤجل إلى Phase 4، والمجزر إلى Phase 5.

## السلوك

- الكارت الرئيسي يعرض متوسط الفروع بعد الخصومات، وأسفله الرقم قبل الخصومات، بدل استخدام «غير مكتمل» كرقم رئيسي.
- عند نقص برنامج مطلوب، متوسط البرامج المتاحة بالتساوي يعطي مؤشرًا مبدئيًا. مثال سبتمبر: FS=90 وGHP=80 وFSMS ناقص → 85% مؤقتًا. عند إضافة FSMS=70 يكتمل التقييم بأوزان 50/40/10 → 84%.
- بعد اكتمال البرامج، الشهور العادية FS/GHP بأوزان 50/50، وشهور 3 و6 و9 و12 بأوزان 50/40/10.
- الزيارات المكررة لنفس البرنامج والفرع والشهر تُجمع بمتوسط البرنامج أولًا. في المؤشر الرئيسي تتساوى الشهور ذات النتائج داخل الفرع، ثم تتساوى الفروع ذات النتائج. الفروع/الفترات بلا درجات لا تُحسب بصفر أو 100%.
- اختيار برنامج واحد يلغي أوزان البرامج الأخرى ويعرض متوسط النوع المختار. اختيار FSMS وحده لا يعتبر الشهور غير الربع سنوية فحوصات مطلوبة ناقصة، لكنه يعرض فحص FSMS مسجلًا خارج تلك الشهور إذا كان موجودًا.
- المسودات تُعد ضمن عداداتها وتظهر في الزيارات، لكنها لا تدخل النسب أو الترتيب.

## الفلاتر والتفاصيل

فلتر الفرع والشهر ونوع الفحص أعلى الصفحة وداخل نافذة الامتثال يتحكمان في نفس الاختيار. الافتراضي الشهر الحالي بتوقيت القاهرة. «مسح الفلاتر» يختار كل الفروع وكل الشهور وكل البرامج. اختيار البرنامج يستخدم الـsnapshot الموجود، ويطبق فلتر البرنامج على استعلامات التفاصيل أيضًا؛ لا ينزل إجابات البرامج الأخرى لمجرد عرض نوع واحد.

تفاصيل الامتثال تعرض ستة تقييمات فرع/شهر في الصفحة، مع بحث باسم الفرع وأزرار تنقل. تظهر طريقة الاحتساب: متوسط المتاح أو وزن البرنامج عند اكتمال الشهر أو بدون أوزان عند اختيار نوع واحد.

آخر التفاصيل يعرض تأثير خصومات الأقسام وتأثير الخصومات العامة منفصلين، بوحدة النقطة المئوية. الحساب هو:

- تأثير الأقسام = النتيجة قبل جميع الخصومات − النتيجة بعد الأقسام وقبل الخصم العام.
- تأثير العام = النتيجة بعد الأقسام − النتيجة النهائية.

تطبق نفس طريقة تجميع الفروع على هذه النتائج. هذه فروق فعلية في النسبة، وليست جمع النسب المكتوبة في سجلات الخصم؛ مثلًا خصم عام مسجل 20% على نتيجة 5% يؤثر فعليًا بـ5 نقاط حتى الصفر، لا بـ20. قد تظهر فروق تقريب 0.01 عند عرض الأرقام.

## ترتيب الفروع

جدول مستقل تحت Dashboard، بمتوسط الزيارات المعتمدة المتاحة لكل فرع بعد الخصومات، من الأعلى للأقل. لا يستخدم أوزان البرامج أو موازنة الشهور؛ هذا مقصود حسب طلب ترتيب المتاح. فرع عنده فحص واحد يأخذ نتيجته، وفرع عنده فحصان يأخذ متوسطهما. لذلك قد يختلف ترتيب الجدول عن قيمة المؤشر الموزون عندما تكتمل البرامج.

نفس فلاتر الشهر والبرنامج والفرع تطبق على الترتيب. يعرض قبل/بعد وعدد الزيارات والبرامج، مع بحث وتقسيم إلى عشر نتائج في الصفحة. الفروع بلا درجات تظهر آخر الجدول وخارج الترتيب. التعادل في النتيجة المعروضة يعطي نفس المرتبة. البحث داخل الجدول لا يغير رقم المرتبة الأصلي.

تصدير Dashboard يتضمن ترتيب الفروع، ويعرض في الملخص التنفيذي حالة المؤشر وتأثير خصومات الأقسام والعامة. تصدير تقرير الفحص نفسه لم يتغير.

## التطبيق والتجربة

1. احفظ عملك الحالي واستخدم فرعًا منفصلًا.
2. فك ZIP هذه الدفعة داخل جذر المشروع، مع الحفاظ على المسارات واستبدال الملفات المناظرة. لا تشغل migrations قديمة أو أي SQL لهذه الدفعة.
3. ابنِ واختبر على Preview قبل الدمج.
4. جرّب الشهر الحالي، وشهرًا ربع سنوي، ونوعًا واحدًا، وكل الشهور. افتح الامتثال وفلتر من داخله، ثم قارن ترتيب الفروع وعدد الزيارات وتصدير Dashboard.
5. الرجوع لهذه الدفعة يكون باسترجاع ملفاتها إلى commit الأب فقط؛ ليس لها تغيير قاعدة بيانات يحتاج rollback.

## التحقق

55 اختبارًا ناجحًا، تشمل أوزان الشهر والمتوسط المبدئي، اختيار النوع، مساواة الفروع والشهور، الترتيب والتكرار والتعادل والفروع بلا بيانات، وحدود الشهر والسنة الكبيسة، وتأثير الخصومات عند الوصول للصفر. تشمل أيضًا اختبارات عرض HTML للتفاصيل والترتيب وتقسيم الصفحات، واختبار طلب Supabase الحقيقي بشبكة وهمية، وتنفيذ SQL السابق على PostgreSQL معزول.

نجح بناء نسخة النشر. فحص TypeScript العام لا يزال يحتوي أخطاء قديمة من المشروع؛ لا يُعد نجاح الاختبارات بديلًا عن تجربة الحسابات والبيانات الفعلية. لم يتم نشر الدفعة أو تعديل قاعدة الإنتاج من بيئة التطوير.
