# حزمة استكمال Phase 3 وPhase 4 ومراجعة Phase 5

هذه الحزمة تُطبّق فوق نسخة Phase 3 السابقة. تشمل أيضًا إصلاح NULL؛ لا تحتاج لتركيب حزمة NULL المنفصلة أولًا. لم تُنشر على الموقع ولم تُنفّذ على قاعدة الإنتاج.

## ما تغيّر

### Dashboard

- رجوع عنوان «فلترة الفترة الزمنية» أعلى الصفحة.
- إزالة البحث النصي من متابعة الفروع والترتيب وتفاصيل المؤشر، واستبداله بفلاتر الفرع والشهر والبرنامج المشتركة.
- تغيير أي فلتر يؤثر على نفس نطاق البيانات في الأرقام والتفاصيل والترتيب، ويعيد صفحات الترتيب والتفاصيل للبداية.
- نسب كروت الأقسام وفروعها وشهورها تستخدم نقاط الملخص بعد خصومات القسم، بنفس محرك الفحص. نسب الأقسام قبل الخصم العام؛ نسبة شهر البرنامج داخل تفاصيل الفرع هي متوسط زياراته بعد جميع الخصومات.
- لم تتغيّر أوزان الشهور أو محرك الفحص أو قاعدة متوسط المتاح والترتيب المتفق عليها.

### Phase 4 — تقرير المفتش

من الإدارة ← المستخدمون ← الضغط على الاسم:

- إجمالي الفحوصات، المعتمد، المسودات، وقائمة بصفحات مع روابط للتفاصيل.
- فلاتر من/إلى، الفرع والبرنامج.
- أعلى وأقل الفروع لكل برنامج بمتوسط الزيارات المعتمدة بعد الخصومات؛ يعرض جميع المتعادلين وعدد الزيارات.
- الأقسام الأكثر فقدًا في النسبة، وفقد درجات البنود منفصلًا عن أثر خصم القسم.
- عدد ونسبة مرات الحصول على 100%، مع ترتيب حسب عدد المرات أو فقد النسبة.
- قبل جميع الخصومات وبعدها، وأثر خصومات الأقسام والعامة منفصلين.
- الفحوصات المسندة حسب auditor_id. المسودات في القائمة والعدادات، ولا تدخل مقارنات التقييم.
- أي فحص معتمد فيه NULL غير N/A في قسم محتسب يُستبعد من المقارنات ويظهر عدده للمراجعة؛ لا نخمن درجته.
- التحليل يُحمّل فقط عند فتح تقرير المستخدم، بدون صور وبحد أقصى 3 طلبات تقرير متزامنة. القوائم تقرأ كل الصفحات ولا تقف عند سقف 1000 سجل. فشل قراءة تقرير يمنع عرض تحليل جزئي.
- لا تُغيّر هذه الميزة RLS أو صلاحيات الخادم؛ تستخدم صلاحيات الحساب الحالية داخل صفحة الإدارة القائمة.

### Phase 5 — إصلاحات المجزر الحالي

لم تُحدد متطلبات لإعادة تصميم دورة عمل المجزر؛ هذا الجزء يعالج عيوب الحفظ والعرض المؤكدة في النموذج الموجود:

- حفظ لقطة كاملة للتقييم الحالي، وبنود الـchecklist ودرجاتها وملاحظاتها، والأوزان ومدة الرحلة والقبول الاستثنائي داخل report_details.
- لا نعتمد على قابلية كتابة أعمدة التقييم القديمة أو نغيّرها؛ التقارير الجديدة تقرأ تقييم اللقطة المحفوظة. المعادلة الحالية كما هي.
- عرض اللقطة عند فتح التقرير، وتصدير Checklist وEntered details مع Grand Total في Excel.
- إدخال سبب الرفض بدل حفظه فارغًا دائمًا. عدادات الأسباب تصف عدد التقارير المطابقة، وتلتزم بفلاتر الصفحة؛ لا تجمع الأرشيف والخادم مرتين.
- توحيد عرض النسب، والتمييز بين نسب الأرشيف الكسرية ونسبة التقرير الجديد، حتى 0% و1%.
- التحقق من الأعداد والأوزان وحالات عدم المطابقة، ومنع النقر المتكرر أثناء الحفظ.
- ربط الصور الناجحة حتى لو فشل بعضها، وإظهار التحذير مع رسالة الحفظ.
- استخدام تاريخ القاهرة بدل التاريخ الثابت في نموذج المجزر، وتاريخ القاهرة في بدء الفحص.
- إظهار تنبيه صريح إذا تعذر تحميل تقارير الخادم أو لم توجد تقارير ويُعرض الأرشيف المحلي. لا تدمج هذه الحزمة الأرشيف مع قاعدة البيانات.
- لا تُستعاد الحقول التي فُقدت بالفعل في التقارير القديمة، ولا تُضاف دورة اعتماد أو تحرير جديدة للمجزر.

### حفظ الإجابات والاعتماد وسجل الفحوصات

- البند الافتراضي يبقى بدرجته الكاملة عند كتابة تعليق، وإلغاء N/A يعيد الدرجة القصوى. الصفر الصريح يبقى صفرًا.
- حفظ الإجابات بالترتيب، وانتظار الحفظ قبل الملخص وإعادة محاولة القيم الفاشلة؛ فشل الحفظ المستمر يمنع فتح الملخص.
- التحميل الخلفي لا يستبدل التعديلات المحلية. هذه ليست ميزة حفظ دون اتصال؛ إغلاق المتصفح أثناء فشل الشبكة قد يفقد تعديلًا لم يُحفظ.
- البنود القديمة NULL تظهر تحذيرًا، والاعتماد يرفضها قبل إضافة الافتراضيات وبعد إعادة القراءة مع أرقام البنود.
- لم تُعدّل الإجابات القديمة الـ22، ولم يُسحب اعتماد أي فحص قائم. راجع درجتها ثم أعد الاعتماد لتحديث الدرجة المحفوظة.
- طلب إنشاء الفحص له UUID ثابت للمحاولة، مع منع النقر المتكرر ومراجعة وجود السجل إذا فُقد رد الإنشاء، بدل إنشاء سجل ثانٍ عند إعادة المحاولة في نفس الصفحة.
- سجل الفحوصات يقرأ بترتيب ثابت وعلى صفحات، ولا يكرر نفس UUID إذا تكرر في نتيجة التحميل، ويعرض معرّفًا مختصرًا لتمييز الزيارات.
- الزيارات ذات UUIDs مختلفة تظل ظاهرة حتى لو لها نفس الفرع والبرنامج والتاريخ؛ قد تكون زيارات صحيحة متعددة. لا يوجد حذف أو دمج تلقائي.
- الاستعلام supabase/diagnostics/possible-duplicate-audits.sql للقراءة فقط، يحدد مجموعات تحتاج مراجعة، ولا يثبت وحده أنها سجلات مكررة.

## التطبيق بالترتيب

1. احتفظ بالنسخة الحالية في فرع منفصل. الحزمة تفترض أن Phase 2 وPhase 3 ووظيفة dashboard snapshot سبق تطبيقها.
2. قبل نشر الملفات: شغّل كامل supabase/migrations/20261024020000_slaughter_report_details.sql في Supabase SQL Editor. يضيف عمود JSONB اختياريًا واحدًا لجدول slaughter_reports الموجود. لا يغير سجلات قديمة أو درجاتها أو الصلاحيات أو RLS. يمكن تشغيله مرة ثانية دون إضافة مكررة. لا ينشئ جداول المجزر الأساسية إذا لم تكن موجودة.
3. فك الحزمة في جذر المشروع مع الحفاظ على المسارات واستبدال الملفات المناظرة. لا تُثبت حزمًا جديدة؛ لم تتغير dependencies.
4. جرّب في Preview مستخدمًا البيانات والصلاحيات الفعلية قبل النشر. لا توجد كتابة على الإنتاج من طرفنا.
5. بعد النشر، أعد فتح الصفحة حتى لا يبقى كود قديم في جلسة المستخدم. الجلسات التي ما زالت تعمل بالكود القديم قد تظل تستخدم مسار الحفظ القديم.

## تجربة القبول

- Dashboard: يظهر العنوان، ولا يوجد بحث نصي. الفرع والشهر والبرنامج يؤثرون على الرقم والترتيب والتفاصيل معًا. قسم بدرجة 50% وخصم قسم 10 نقاط يعرض 40%، والصفر يبقى محسوبًا.
- الفحص: تعليق على بند جديد يحافظ على الدرجة القصوى؛ N/A ثم إلغاءه يعيد الدرجة القصوى؛ صفر ثم تعليق يظل صفرًا. الانتقال فورًا للملخص ينتظر الحفظ. تعطيل طلب الحفظ يمنع الانتقال.
- فحص قديم له NULL: يظهر التحذير ولا يُعاد اعتماده قبل الاختيار الصريح للدرجة الصحيحة أو N/A. لا تحوّل كل NULL تلقائيًا إلى 4 أو صفر.
- الإدارة: اسم المستخدم يفتح التقرير. جرّب الفلاتر، فحصًا درجته صفر، مستخدمًا بلا فحوصات، والتعادل. تغيير المستخدم يغيّر بيانات التقرير. تحقق أن المستخدم العادي لا يفتح صفحة الإدارة.
- الإنشاء: نقرتان سريعًا لا تنشئان فحصين. إعادة المحاولة بعد فقد رد الحفظ تستخدم نفس UUID في نفس الصفحة. فتح صفحة إنشاء جديدة أو جهاز آخر يمثل طلبًا مستقلًا، وليس منعًا لكل الزيارات المتشابهة.
- المجزر: احفظ تقريرًا بملاحظات وأوزان وسبب رفض وتقييم، ثم أعد تحميل الصفحة وافتحه وصدّره. افحص 0% و1%، والفلاتر وعدادات أسباب الرفض. جرّب فشل صورة والتأكد من ظهور التحذير، ثم تحقق من الصور على البيئة الفعلية.

## التحقق المنفذ وحدوده

- 82 اختبارًا نجحوا، بما فيهم 7 اختبارات RPC على PostgreSQL/WASM معزول، واختبارات محتوى واجهة الفلاتر وتقرير المفتش عبر server rendering.
- اختبار مستقل لترحيل المجزر نجح: التشغيل مرتين، بقاء البيانات القديمة والدرجات وRLS والسياسات، وحفظ JSON ودرجة صفر واسترجاعهما.
- البناء نجح. فحص TypeScript العام ما زال يفشل بأخطاء سابقة؛ لم تُضف أخطاء جديدة مقارنة بنتيجة ما قبل هذه الدفعة بعد تجاهل تحرك أرقام الأسطر.
- لم تُنفذ تجربة بصرية تفاعلية داخل متصفح؛ Chromium غير متاح في بيئة التنفيذ. اختبارات العرض هي server rendering، ولا تحل محل Preview بالحسابات الحقيقية.
- لم يُقَس الأداء على الإنتاج. فتح تقرير مفتش ذي عدد كبير من الزيارات قد يستغرق وقتًا؛ الطلبات محدودة التزامن ولا تحمّل صورًا ولا تعطل Dashboard.
- لم تُشخّص السجلات القديمة المتشابهة على الإنتاج؛ يلزم تشغيل استعلام القراءة ومراجعة UUIDs. لا ندّعي أنها كلها تكرار تقني.

## الرجوع

ارجع لنسخة التطبيق السابقة من فرعك. اترك report_details في قاعدة البيانات كي لا تفقد تفاصيل التقارير الجديدة؛ لا تحذف العمود. الإصدار القديم يتجاهله. الرجوع للكود القديم يعيد أيضًا عيوب حفظ الإجابات التي أُصلحت؛ راع ذلك عند اختيار النسخة.
